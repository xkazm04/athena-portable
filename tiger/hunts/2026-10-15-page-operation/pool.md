## P01 - Compile proven Tier-2 DOM traces into replayable Tier-1 page macros

`leap` `effort M` round 1 - anchors 7/7 - peers 5/10 (n=3)

- **Outcome:** After Athena successfully completes a multi-step DOM interaction on a non-WebMCP site once (such as filtering a table, filling a multi-field modal, and clicking save), she can distil that proven episode trace into a provenance-backed, parameterized page macro that appears on future turns for that origin as a single GATED tool call—collapsing 5–8 rounds of DOM hand calls into one reviewable card and one round.
- **Builds on:** Evolves the unified Tier-1/Tier-2 HostToolDef contract (ADR 0065) and activates the already-implemented, provenance-checked procedural memory store in Brain.write_procedural and Recall.
- **Mechanism:** 1) Register `core.write_procedural` in `src/athena/core/catalog.py:164-230` (`CoreServices` at `catalog.py:100-115`) wired to `Brain.write_procedural` (`src/athena/core/brain/store.py:460-518`), enforcing `_require_provenance` (`store.py:360-379`) against live `[host:<app_id> tier2]` episode IDs written by `BrowserLane._record_results` (`src/athena/lane/browser_lane.py:372-388`). 2) Define a structured `scope="action"` procedural payload (`store.py:64`) capturing the origin `app_id`, parameter JSON Schema, ordered step descriptors (`page_find` role/label/name query from `hands.js:236-267` followed by `page_fill`/`page_select`/`page_click`), and expected post-condition. 3) When building the turn manifest in `apps/desktop/src/lib/manifest.ts:105-124` and `apps/desktop/src/lib/hands.ts:156-159`, merge active `scope="action"` procedures for `host:<app_id>` as synthetic `GATED` tools (`host.<app_id>.macro_<slug>`, `runner: "shell"`). When the user approves the single macro card (`src/athena/lane/browser_lane.py:333-350`), the shell runner (`apps/desktop/src-tauri/src/hands.rs:146-188`, `hands.js:401-428`) replays each step deterministically inside the page—minting and resolving fresh refs per step and aborting immediately on selector mismatch or navigation (`hands.js:443-455`).
- **Evidence:** Observed in code and UAT: `Brain.write_procedural` (`src/athena/core/brain/store.py:460-518`) and `Recall._always_block` / `_keyword_block` (`src/athena/core/recall.py:481-528`) are already shipped and tested for `DISTILLED_KINDS = ("fact", "procedural")`, yet `core_entries` (`src/athena/core/catalog.py:164-230`) exposes only `recall`, `write_fact`, and `checkpoint`—leaving procedural memory unreachable during live runs. Meanwhile, `brief.md:189-190` notes that Tier-2 hands are one call per OP against an 8-round ceiling (`src/athena/harness/rounds.py:54`), making multi-step DOM workflows slow and brittle.
- **Risk:** A DOM macro could replay against a redesigned page layout and click the wrong control. Mitigation: every macro is forced to `GATED` in `hooks.py:251-275`, resolves elements by semantic `{role, label, name}` (`hands.js:58-78`) rather than brittle XPaths, requires an exact unique match (`matches.length === 1`) at each step before acting, and halts on the first mismatch or `generation` bump (`hands.js:443-446`).
- **Verify:** On a non-WebMCP test page (e.g. a 4-field filter-and-update workflow), completing the task via Tier-2 hands in turn 1 and distilling it via `core.write_procedural` produces a `host.<app>.macro_*` tool on turn 2 that executes the same workflow in 1 round and 1 approval card instead of >=4 rounds and >=3 cards.
- **Why it matters:** Turns every web app the user operates into a self-upgrading WebMCP surface: Athena enters any legacy SaaS via Tier-2 DOM hands on day one and graduates her own proven interactions into fast, single-card Tier-1 capabilities with full episodic provenance.
- **Anchors:** `src/athena/core/brain/store.py:64`, `src/athena/core/brain/store.py:460-518`, `src/athena/core/recall.py:481-528`, `src/athena/core/catalog.py:164-230`, `src/athena/lane/browser_lane.py:372-388`, `apps/desktop/src-tauri/src/hands.js:236-267`, `apps/desktop/src/lib/hands.ts:156-159`

## P02 - Add bounded batch and form-plan execution to collapse per-item gate fatigue

`extend` `effort M` round 1 - anchors 7/7 - peers 6/10 (n=3)

- **Outcome:** Users can review, selectively uncheck items in, and approve a batch of homogeneous Tier-1 calls (such as sending 37 overdue invoice reminders) or a multi-field Tier-2 form fill on a single approval card, executing the approved slice with one signature and one continuation turn.
- **Builds on:** Builds directly on the persisted ApprovalGrant parameter-binding contract in `ApprovalsStore` and `BrowserLane.answer_decision` (`ADR 0010`), where the daemon replays server-stored parameters into `Execute` frames.
- **Mechanism:** 1) Add `page_form_fill` to `HANDS` (`apps/desktop/src-tauri/src/hands.rs:106-133`, `apps/desktop/src-tauri/src/hands.js:286-357`) accepting `fields: [{ref, action: "fill"|"select"|"check", value}]` plus optional `submit_ref`, validating all refs up front before mutating any field. 2) Extend `GateHook.run_tool` (`src/athena/harness/hooks.py:118-174`) and `ApprovalsStore.create` (`src/athena/core/approvals.py:164-196`) so a `GATED` Tier-1 tool call can carry a bounded `batch_items: list[dict]` payload (capped at `MAX_BATCH_ITEMS = 25` in `src/athena/core/validators.py`). 3) Extend `ApprovalDecision` and `BrowserLane.answer_decision` (`src/athena/lane/browser_lane.py:310-358`) with `approved_indices: tuple[int, ...] | None` so the user can deselect individual rows on the card before approving; `answer_decision` replays `self.gate.run_tool` for the approved subset and emits sequential `Execute` commands (`apps/desktop/src/stores/run.ts:618-654`, `902-917`) with fail-fast abort on the first bridge error and a single aggregated continuation turn (`run.ts:913-917`).
- **Evidence:** Observed in UAT r1 (`uat/runs/2026-10-01-r1/SUMMARY.md:18-21`, `30-42`, findings `mira-2`, `mira-5`, `jonas-3`): sending a single overdue reminder took ~9.5 min wall and ~$1.60 in model calls, and Mira's real workload is ~37 overdue invoices at a time—impossible under one-call-per-OP and `MAX_ROUNDS = 8` (`src/athena/harness/rounds.py:54`).
- **Risk:** Mid-batch failure on item K of N could leave partial side effects unclear to the user and model. Mitigation: execute items sequentially in `run.ts:902-917`, halt immediately on the first `isError` result, mark per-item status (`succeeded`, `failed`, `skipped_after_error`) on the card and in `BrowserLane._record_results` (`browser_lane.py:372-388`), and feed the exact per-item ledger into the single `continueTurn` call.
- **Verify:** Chasing 10 overdue invoices in `examples/demo-kit` completes in 2 model rounds and 1 approval card (with per-item deselection verified by unchecking 2 of 10 rows and confirming exactly 8 `send_overdue_reminder` calls fire), down from 10 approval cards and >8 rounds.
- **Why it matters:** Transforms Athena from a single-record assistant into an operational batch workbench while strengthening—not weakening—the human gate, because reviewing one comparative table of 20 actions is far less error-prone than rubber-stamping 20 separate cards.
- **Anchors:** `uat/runs/2026-10-01-r1/SUMMARY.md:18-21`, `src/athena/harness/rounds.py:54`, `src/athena/harness/hooks.py:118-174`, `src/athena/core/approvals.py:164-196`, `src/athena/lane/browser_lane.py:310-358`, `apps/desktop/src/stores/run.ts:902-917`, `apps/desktop/src-tauri/src/hands.js:286-357`

## P05 - Harden the bridge-to-memory loop: schema check, drift pin, and tool role tag

`deepen` `effort S` round 1 - anchors 8/8 - peers 3/10 (n=3)

- **Outcome:** Page tools cannot be called with schema-invalid arguments, a trusted origin cannot silently rewrite tool descriptions or weaken safety flags via `toolchange` after consent, bridge errors surface with exact machine-readable reasons instead of collapsing to `unknown`, and untrusted page tool outputs are never stored or recalled with a `system` role badge.
- **Builds on:** Tightens the existing four-layer safety chain across `packages/athena-bridge`, `apps/desktop/src/stores/origins.ts`, `src/athena/contracts/harness.py`, and `src/athena/lane/browser_lane.py`.

- **Evidence:** Observed directly in the codebase and documented in `brief.md:94-95`, `130-151`: `8cdf1e9` previously failed because `inject.js` emitted error codes not registered in `ERROR_REASONS` (`harness.py:119-139`); `door.ts:27-62` sets `sideEffects: "data"` which `gate.js:25` (`SIDE_EFFECTS = ["none", "internal", "external"]`) rejects; `bridge.ts:83` re-lists tools on `toolchange` with no digest check against `origins.ts:93-128`; and `browser_lane.py:385` writes `self._append(..., "system", ctx)` even though `store.py:63` already defines `"tool"` in `EPISODE_ROLES`.

- **Why it matters:** Closes four real trust holes in one cohesive sweep—ensuring that untrusted page code cannot smuggle prompt injections through post-consent `toolchange` events or masquerade as `system` memory on future turns.

## P06 - Approve the intent, not each click: one bound card for a page_sequence

`deepen` `effort M` round 1 - anchors 8/8 - peers 7.3/10 (n=3)

- **Outcome:** On an app with no WebMCP tools the user approves 'fill Client, fill Amount, choose Net 30, click Save' as ONE card listing the steps in order. It runs exactly those steps, in that order, at most once. If any target has moved since the card was filed, nothing runs. Today the same draft is 3-4 independent cards. They can be approved in any order (Save before the body is filled), and each approval costs another model turn.
- **Builds on:** The single-use, parameter-bound grant (approvals.matches canonicalises params, consume spends once, Execute replays params from the row) and the minted-ref hands. A sequence is one more hand whose parameter is an ordered list, so the grant binds the order as well as the values.
- **Mechanism:** Add a tenth row page_sequence to HANDS (reversible:false, side_effects:'internal', runner Page), mirrored in hands.js FLAGS so the existing parity tests hold. Schema: steps = array, minItems 2, maxItems 8. Each item has hand (enum page_fill|page_select|page_click|page_submit|page_scroll|page_wait), ref (maxLength 64), value (maxLength 2000) and text (maxLength 200); the description (<=240 chars, ADR 0068) spells out the item shape. hands.js runs it in two passes in one task. Pass 1 is a pre-flight: resolve every ref and apply the checks page_fill/page_select/page_click already make (disabled, select vs field, inside a form). If any step fails, the whole sequence is refused and the failing step is named. Pass 2 executes the steps in order, stops at the first refusal, and answers one line per step plus '(ran k of n)'. Extend validators._check_value to recurse into object properties/required, so the gate validates every step before a card is filed; today an object item's inner fields go unchecked. The card renders the steps as a numbered list. Gate, approvals and lane are unchanged: the flags give GATED, the grant canonicalises the whole list, and Execute carries it from the row.
- **Evidence:** Observed in code: every approved card's execute rows go through onPage and then start a fresh continuation exchange (run.ts:913-917), so N gated hand steps cost N cards plus N model turns. The op grammar lets one reply carry several OP lines, rounds.py files a card per op, and cards are answered independently, so execution order follows the order the user taps, not the order proposed. README act 2 ('each fill is a decision card') on a tier-2 app is 3 cards per draft (fill, fill, save) and 9 for three drafts; with a sequence it is 1 per draft. That is arithmetic from the code paths, not a measured run.
- **Risk:** Bundling may lower attention per step, and a long list may get rubber-stamped. Mitigation: cap at 8 steps; the card lists every step uncut (the card already promises params are never cut); the pre-flight means a stale page runs nothing; the class can never drop below GATED. A partial run (navigation mid-list) only ever executes a prefix of what was approved, and says so.
- **Verify:** Headless run-loop test on a no-WebMCP fixture form (3 fields + Save). Before: 4 decision.requested events and 4 continuation exchanges. After: 1 card, 1 continuation, fields saved in proposal order. A sequence whose 2nd ref was detached before approval runs zero steps and answers unknown_ref naming step 2. A page_fill step aimed at a select is refused validator_failed before any card is filed. hands.rs parity tests and tests/test_refusal_parity.py stay green.
- **Why it matters:** Tier 2 (which covers nearly every page) stops being a click-by-click permission slog: a person approves what they mean, and the system's exactly-once guarantee extends from parameters to order.

- **Outcome:** Once an origin is trusted, a page that rewrites a tool's description, schema or flags must win a new card before that tool can run unattended again. The card shows the old contract and the new one.
- **Builds on:** First sight and pins already tighten, and a loosening override is already refused. Trust is currently per origin, and a later edit of the same tool name inherits it.
- **Mechanism:** On every successful list, the surface hashes each tool's name, description, canonical input schema, reversible and side_effects. The hash recorded when the origin was trusted is the contract the user accepted. A different hash adds host.<app>.<tool> to the gated_tools list the snapshot already sends, and the existing _tightened path files a card. The slip shows the previous description and schema beside the new ones, both neutralised and cut with (showing N of M). Decline leaves the old hash in force. Only a successful approved execute stores the new hash. toolchange stays payload-free; the surface keeps re-listing and diffs locally, so the wire format does not change. This amends ADR 0063 and needs that amendment written down. It adds no pin control.
- **Evidence:** Observed in the code and called out as a registry deviation: onToolChange re-lists with no diff, and the comment in bridge.ts records that choice. inject.js posts toolchange with no body. After first sight, an AUTO tool whose description changes from 'list invoices' to 'send every invoice' still runs unattended if its flags stay reversible. Hypothesis: pages and extensions will edit registrations after load, because the demo kit re-registers when the description or the schema changes.
- **Risk:** A chatty page that rewrites descriptions every load would ask for a card on every visit. The hash covers only description, schema and flags, and an approved execute settles it, so an identical re-registration does not ask again.
- **Verify:** Trust an origin whose list_invoices tool is reversible with side_effects none, and confirm a call is AUTO. Change only the description to 'Send every invoice' and keep the flags. The next OP is pending_approval, and the slip contains both descriptions. Decline, call again, and it is still a card. Approve and execute, then an unchanged description is AUTO again. Before the change, the same edit stays AUTO.
- **Why it matters:** Trusting an origin stays safe after the page updates. The gate's tighten-only rule starts to follow the tool the user actually read, which is what makes a standing AUTO survivable.
