# Avatar measure: which machines get neural motion by default (ADR 0120 follow-up)

The face helper (`src/athena/channels/voice/face_helper/`) runs JoyVASA per sentence to give Athena
neural head, lid, gaze and brow motion. Without it she uses procedural motion. This spike answers
two questions on the **shipped code path**:

1. Which machines can run that motion fast enough to see it?
2. What would make it fast enough everywhere?

Everything here is reproducible with the scripts listed under **Reproduce**. Data (audio, tracks,
checkpoints, logs) lives in `~/.athena-avatar/measure/`, never in the repo. Raw results are in
`results/`, and `results/summary.md` is regenerated by `summarize.py`.

**Machine:** AMD Ryzen 7 7800X3D (8 cores / 16 threads), RTX 4090, 64 GB RAM, Windows 11, torch
2.7.1+cu128, onnxruntime 1.31. **Date:** 2026-10-18.

**Caveat that applies to every CPU number below.** The box was shared. Other sessions and a WSL VM
kept it at 92-100 % busy for the whole run, and nothing could be done about it. Each row records
the load it ran under (`machine_busy_pct`). The bench processes and their Kokoro children ran at
HIGH priority class, so these numbers lean pessimistic for a machine that only runs Athena. Read
them as relative, not as a dedicated-machine spec.

## Findings first

- **The shipped helper cannot run motion on a CPU at all.** `LivePortraitWrapper` picks `cuda:0`
  whenever MPS is absent, so on a machine without CUDA `Motion()` fails with "Attempting to
  deserialize object on CUDA device 0". The helper then reports `caps motion:false`. The benches
  below set `flag_force_cpu`, a one-line fix: `flag_force_cpu = not torch.cuda.is_available()`.
  Today the answer to "which machines get neural motion" is "only CUDA machines", by accident.
- **Cost is a step function of 4 s windows.** JoyVASA always generates 100 frames (4 s). Within each
  unpinned config, a 1.2 s and a 3.3 s sentence cost the same, 6.1 s costs about 2x and 9.6 s about
  3x (ratios 0.99-1.17 / 1.92-2.17 / 3.01-3.25 across configs). So one warm 1-window probe predicts
  every sentence.
- **The denoiser is 85 % of CPU time.** Each window runs 50 DDPM steps, each a batch of 2 for CFG.
  HuBERT is about 10 % and the rest (librosa resample, retarget) about 4 %.
- **Live, on a CPU, motion is late by its whole compute time.** On a CPU-only machine Kokoro (2
  threads) and JoyVASA share the cores. Kokoro took 3.7-4.4 s per sentence here, slower than
  playback, so every sentence starts playing the moment it is rendered and its motion starts at
  that same moment. Isolated warm RTF (0.55-0.93) made 4-8 threads look viable. The live schedule
  said 2-44 % of speech got neural motion.
- **Two cheap changes make a 4-thread CPU match the RTX 4090 baseline:**
  - A 10-step DDIM sampler, which needs no retraining because the model predicts x0.
  - Not loading LivePortrait's renderer modules, which motion never uses (−600 MB RAM).

  Together: 80 % of speech covered live and 96 % when Kokoro runs ahead, against CUDA's 82 % and
  96 %. The cost is some motion: roll amplitude 0.66x, and head error to the default 0.66° against
  0.53° between two seeds of the unchanged model.

## Part A: measurements

### Method

- **Audio.** Kokoro af_heart, rendered the daemon's way (`render.py`): s1_5 = 1.19 s, s3 = 3.26 s,
  s6 = 6.08 s, s10 = 9.58 s. There was no clean 1.5 s cut; 1.19 s is the same single window.
- **Motion** (`bench_motion.py`). This is the shipped `face_helper.motion.Motion.frames` (WAV round
  trip, librosa, JoyVASA, decoder, retarget). One fresh process per configuration:
  - cold load is `Motion()` construction;
  - "first motion ready" is process start through imports, load and the helper's own 1 s warm-up
    tone;
  - then 3 warm repetitions per sentence.

  3 processes per configuration give **n = 9 per cell** (median, min-max). Configs:
  - torch intra-op threads 4 / 8 / 16;
  - `aff4-t4`, pinned to logical CPUs 0,2,4,6 (one thread on each of 4 physical cores);
  - `aff2-t2`, pinned to 0,2;
  - CUDA, under `gpulock.py`.
- **Memory and CPU.** Peak working set comes from `K32GetProcessMemoryInfo`. "Cores used" is
  process CPU-seconds divided by wall time.
- **Visemes** (`bench_visemes.py`). The shipped `sentence_visemes` with tokens and the silence time
  map made exactly as the daemon makes them. Durations subgraph on onnxruntime CPU;
  `intra_op_num_threads` 2 (shipped) / 4 / 8 / 16 and the pinned proxies. 3 processes × 7 reps
  (n = 21).
- **Live schedule** (`live_replay.py`). A 5-sentence line (2.3 / 3.8 / 2.4 / 6.7 / 3.2 s). It
  follows the shipped `synthesize_face` schedule:
  - Kokoro renders back-to-back (the daemon does not pace audio), each a real sherpa run using
    `FACE_ARGS`, as a child of the bench process so it shares the cores and pinning;
  - each sentence goes to a FIFO motion worker the moment its render finishes;
  - the client plays sentence k at max(end of k−1, render-done(k) + 0.1 s for visemes).

  Motion for k is in time when it is done by k's play start. "Coverage" is the share of speech time
  that has neural motion. `--kokoro none` releases all five pre-rendered sentences at once: the best
  case for audio and the worst queue for motion. 3 lines per config.
- **Quality** (`quality.py`, `metrics.py`). Each variant's RigParams after the shipped retarget,
  compared with the default (seed 7, 50 steps). Measures: head RMS in degrees, per-channel
  correlation, amplitude (std ratio), and blink onsets matched within 200 ms. The **noise floor** is
  seed 7 against seeds 8 and 9 of the unchanged model; JoyVASA samples, so only distances relative
  to it mean anything. Run on 30 held-out corpus sentences (2.5 min of audio, `q2`) and on the 4
  bench sentences (`q`).

### A.2 The "small machine" proxy, and why it failed here

The proxy was 4 torch threads pinned to 4 physical cores (logical 0,2,4,6), plus a 2-core variant.
A pinned process cannot move off cores the background is using.

- With the WSL VM saturating the box (its virtual CPUs are not preempted by a HIGH-priority
  process), the pinned 4-core run got only 1.6 cores of CPU. It came out slower than the pinned
  2-core run and 2-6x slower than 4 unpinned threads, with a wide spread.
- The ONNX experiment (A.5) shows the same window pinned: torch 6.1-9.8 s, onnxruntime 1.2-6.2 s.
  So torch's OpenMP pool, not the work itself, degrades worst under pinning plus contention.

**The pinned rows are not a laptop measurement and not even a good proxy on this box.** Use "CPU 4
threads" (unpinned, 2.8 cores actually used) as the best available small-machine stand-in. A real
4-core laptop also has lower all-core clocks, a smaller cache than the 7800X3D's 96 MB and thermal
limits, so expect it to be slower than that row. **Not verified:** any real laptop.

How to read this table:

- **The first sentence is always late** by its compute time. There is nothing to overlap it with,
  and the crossfade is there to absorb it.
- **"live" is the render-gated regime.** Kokoro took 3.7-4.4 s per sentence here, slower than
  playback, so there were 3.3-5.6 s of audio gaps per line from Kokoro alone. In this regime motion
  is late by its own compute time on every sentence, so coverage ≈ 1 − compute/duration. This is the
  realistic regime on a CPU-only machine, where Kokoro and the motion model share the cores.
- **"ahead" is the best case for audio.** The queue is what matters there: a sentence is in time when
  all motion before it finished within the audio before it.
- **An idle machine falls between the two rows** of the same config.

## A.4 → the default-on rule, and the probe

**What the user sees** is coverage: the share of her speech carrying neural motion. In the
render-gated regime (a CPU-only machine) a sentence of duration d gets about 1 − W·windows(d)/d,
where W is the warm cost of one 4 s window. In the Kokoro-ahead regime the FIFO queue keeps up
when W is below the shortest sentence (about 1.2 s). Measured:

| W isolated (A.1/A.5) | W live (one-window sentences in the replay, median, with Kokoro running) | config | coverage, live / ahead |
|---|---|---|---|
| 0.58 s | 0.74 s (0.64-0.85) | RTX 4090 | 82 / 96 % |
| 0.63 s (8 thr) | 0.83 s (0.78-0.91) | CPU 4 threads, lean + DDIM 10 | 80 / 96 % |
| 1.32 s | 1.36 s (1.27-1.57) | CPU 16 threads | 67 / 92 % |
| 1.80 s | (see A.4) | CPU 8 threads | 44 / 77 % |
| 2.64 s | (see A.4) | CPU 4 threads | 2 / 0 % |

**Proposed rule.** Neural motion is on by default when the helper's own probe measures **W ≤ 1.0 s**
at the step count it will use; otherwise procedural motion. On this box every config whose live
window was ≤ 0.85 s covered at least 80 % of speech live and 96 % with Kokoro ahead. The next one up
(1.36 s) covered 67 % live. The probe runs while Kokoro is idle, so it reads closer to the isolated
column, about 0.2 s under the live one. The 1.0 s line sits in the gap between 0.83 and 1.36 with
that offset allowed for. Anything under 70-80 % reads as "sometimes neural, sometimes not", which is worse
than consistent procedural motion.

**The probe** fits into the helper's existing warm-up, which already runs a 1 s tone through the
cold model:

1. Load lean (skip F/M/W/G/S). Use `flag_force_cpu = not torch.cuda.is_available()`, and set torch
   threads to the physical core count minus 2, leaving room for Kokoro's 2.
2. Run the 1 s tone once (cold, as today, to warm the kernels). Then run it **twice more at 10 DDIM
   steps**, timing each. Take W10 as the median and A as the timed audio-encoder share (the wrapper
   already exposes `extract_audio_feature`).
3. Predict W for K steps: W_K ≈ A + (W10 − A)·K/10, plus "other". Choose the largest K in
   {50, 25, 10} with W_K ≤ 1.0 s. If even W10 > 1.0 s, set motion off with
   reason `"too slow here (window 1.4 s > 1.0 s)"`.
4. Report it in `caps`: `{"motion": true, "steps": K, "window_s": W_K}`. The daemon's `face` engine
   row can show it, and an explicit setting can override it either way.
5. Re-probe only on helper start. A machine on battery or thermally throttled will measure slower
   and fall back by itself.

That costs about 2 × W10 (≤ 2 s) once, inside a warm-up that already takes 11-20 s. Under this
rule:

- the 4090 runs K = 50 (W ≈ 0.6 s);
- this desktop on CPU runs K = 25 at 16 threads (isolated ≈ 0.75 s, below 1.0 s even with the
  live offset) or K = 10 at 4-8 threads;
- a 2-core machine falls back to procedural motion;
- a real 4-core laptop at lower clocks is predicted to sit near the line, roughly K = 10 at
  0.7-1.1 s. **Not verified.**

### B.2 Distillation proof (`distill/`)

- **Data.** 480 prose sentences from this repo's docs, rendered by Kokoro af_heart (35.1 min).
  Teacher tracks come from the shipped helper on the 4090: seeds 7 and 8 on all sentences, seed 9
  on the test set, about 8.5 min per seed. The split is 408 train, 24 validation (for checkpoint
  selection) and 48 test, the test set never seen in training or selection.
- **Evaluation.** The student's output goes through the **shipped `retarget` unchanged** and is
  compared with seed 7 on the 48 test sentences.

| | attempt 1: log-mel → 66 values | **attempt 2: JoyVASA's HuBERT features → 7 values** | noise floor (seed 7 vs 8, 9) | no motion |
|---|---|---|---|---|
| params, training | 0.63 M, 12 min on 4090 (29.6k steps) | 0.59 M, 10 min (best at step 14.3k of 27.4k) | | |
| head RMS to teacher | 1.28° | **0.74°** | 0.53° | 1.28° |
| yaw / pitch / roll corr | 0.11 / 0.18 / 0.29 | **0.81 / 0.87 / 0.75** | 0.93 / 0.96 / 0.82 | — |
| yaw / pitch / roll amplitude | 0.11 / 0.12 / 0.11 | **0.83 / 0.91 / 0.74** | 1.02 / 1.02 / 1.01 | 0 |
| blinks: recall / precision vs teacher | 0.03 / 0.40 (5 blinks for 66) | **0.58 / 0.61** | 0.61 / 0.56 | 0 |
| CPU time, 3.26 s sentence | 18 ms (ORT, 1 thread) | **0.27 s HuBERT + 11 ms GRU (4 threads)** | | |
| CPU time, 9.58 s sentence | 37 ms | 0.80 s + 34 ms | | |

What changed between the attempts:

- **Attempt 1 failed honestly.** It regressed to the mean, keeping about 11 % of the head amplitude,
  and is no better than no motion.
- **Attempt 2 changed three things:**
  - the teacher's own features;
  - only the 7 values `retarget` reads (pose plus the decoder's 4 projections; the 63 expression
    values are rebuilt with the pseudo-inverse);
  - whole sentences from their first frame instead of random 4 s crops (JoyVASA's track depends on
    where each window starts).
- **Result.** Blink timing matches the teacher as well as two teacher seeds match each other. Head
  correlation is 0.75-0.87 with 74-91 % of the amplitude, sitting between "another JoyVASA sample"
  and "no motion", nearer the former. Training overfit fast (train loss 0.20-0.26 against validation
  0.93), so more teacher data is the obvious lever, and it is free to generate.
- **Speed.** About 0.28 s per window on 4 threads, 10x less than JoyVASA's 2.6-3.0 s there, and
  under the 1.0 s probe budget on any machine that runs HuBERT in under about 0.95 s. That is everything
  measured here except the contaminated pinned runs.

**Not verified:** how the attempt-2 motion *looks* on the owl and origami rigs. That needs an
operator side-by-side, as the spike's A/B did. Also unverified: a CPU-only training run, and
HuBERT on onnxruntime inside the student (0.14-0.25 s per window measured standalone in A.5).

## Recommendation

1. **Now (small, in the helper).**
   - Force CPU when there is no CUDA (motion is broken there today).
   - Load lean (−600 MB).
   - Add the DDIM sampler with K picked by the probe above.
   - Put the probe and the W ≤ 1.0 s rule into `caps`.

   This turns "CUDA only" into "CUDA plus 4+-core desktops", with a measured quality cost of about
   0.1° head RMS beyond the noise floor at K = 10 and some lost roll amplitude. That amplitude can be
   restored with a gain in `retarget`.
2. **Next (the faster model).** Distill properly:
   - 5-10k teacher sentences (about 2-3 GPU-hours), several seeds per sentence, plus validation by
     the operator's eye on both forms;
   - HuBERT on onnxruntime; ship the GRU as ONNX (2.5 MB).

   The helper then needs no torch at all, which also answers the installer question (numpy,
   onnxruntime, librosa). Target: ≤ 0.3 s per sentence on 4 threads, motion on by default for
   essentially every machine that can run Kokoro.
3. **Hold:** ARTalk (pose and blink, MIT) as the fallback if the JoyVASA weight or data provenance
   check fails. Consider the Audio2Face-3D eye channels only if gaze becomes a priority.

## Reproduce

All commands run in the face env (`~/.athena-avatar/venvs/t4-hybrid/Scripts/python.exe`), from
this directory, with `PYTHONIOENCODING=utf-8`. CUDA steps go through
`../../../spark-athena-avatar/spikes/avatar/tools/gpulock.py`.

| what | command |
|---|---|
| bench audio | `python render.py lengths`, `python render.py line` |

| A.3 | `python bench_visemes.py` |
| A.4 | `python run_matrix.py replay` |
